# 三级缓存三档压测报告（验证用户声称数据）
## 压测环境
- 接口：GET /ticket/list/1（TicketListCacheService 三档：mysql 直查DB / redis L2+DB / caffeine L1+L2+DB）
- 工具：node fetch（单机 HTTP），Tomcat 默认 200 线程
- 并发 100 × 10s 主测；并发 300/500 辅助测瓶颈

## 实测结果（并发 100）
| 档位 | QPS | avg | p50 | p95 | p99 | errors |
|---|---|---|---|---|---|---|
| mysql | 1882 | 53.1ms | 49.5 | 85.3 | 101.8 | 0 |
| redis | 5155 | 19.3ms | 18.6 | 31.2 | 42.8 | 0 |
| caffeine | 6787 | 14.7ms | 16.0 | 26.8 | 37.2 | 0 |

## 提升倍数（实测）
- caffeine vs redis：6787/5155 = 1.32 倍
- caffeine vs mysql：6787/1882 = 3.61 倍
- redis vs mysql：5155/1882 = 2.74 倍

## 与用户声称对比
| 指标 | 用户声称 | 实测 | 判定 |
|---|---|---|---|
| QPS 绝对值 | 11570/48819/80393 | 1882/5155/6787 | 量级不同（见瓶颈分析） |
| caffeine/redis 提升 | 2.73 倍 | 1.32 倍 | 方向一致但幅度夸大 |
| caffeine/mysql 提升 | 6.12 倍 | 3.61 倍 | 方向一致但幅度夸大 |
| redis/mysql 提升 | 4.22 倍(隐含) | 2.74 倍 | 方向一致 |

## 瓶颈分析（为何绝对 QPS 无法复现）
1. node 单机 fetch 客户端上限：单进程 HTTP 并发约 7000-8000 QPS 封顶（caffeine 从并发100→500，QPS 6787→7396 只+9%）
2. Tomcat 默认 200 线程池：HTTP 连接是瓶颈，非缓存层
3. 用户声称的 8 万 QPS 需：ab/wrk 本机工具（不走 node 事件循环）+ 调大 Tomcat 线程 + 更高并发
4. 缓存的真实差异在"回源率"：mysql 每次查DB / redis 每请求网络IO / caffeine 进程内命中——延迟递减 53→19→14ms 已清晰体现

## 结论
- **缓存层级提升的方向完全正确**：mysql→redis→caffeine 延迟单调递减（53→19→15ms）、QPS 单调递增（1882→5155→6787）
- **但用户声称的倍数（2.73x/6.12x）在本机环境偏大**：实测 1.32x/3.61x（受 HTTP 栈瓶颈压制，caffeine 的进程内优势被网络层摊薄）
- **建议简历表述**：改为"mysql→redis→caffeine 三档压测，QPS 1882→5155→6787，延迟 53→19→15ms，二级缓存较单级 Redis 提升 32%、较 MySQL 提升 3.6 倍"（真实可复现）
